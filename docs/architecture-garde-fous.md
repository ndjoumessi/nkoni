# Garde-fous EXÉCUTABLES (listes manuelles & prose)

> Référence détaillée pointée par `CLAUDE.md` (§ Garde-fous EXÉCUTABLES). `CLAUDE.md` garde le
> catalogue des tests + la MÉTHODE (saboter dans la direction utile, éviter le test vacant / le
> sabotage inopérant, dériver plutôt que garder, piège ajv) ; ce doc porte le détail par test —
> défauts vécus, angles morts, motifs — qui explique pourquoi chaque garde existe sous cette forme.

Plusieurs invariants du projet reposent sur des listes tenues à la main, que `tsc`/`oxlint` ne peuvent pas vérifier : une liste littérale valide compile. Chacune a donc son test de parité, et la règle est **d'ajouter le garde plutôt que de corriger l'occurrence**.

- `tests/runUnscoped-allowlist.test.ts` — tout appel `runUnscoped` doit être inscrit et justifié.
- `tests/tenant-scoped-models.test.ts` — DEUX gardes : parité `SCOPED_MODELS ↔ schéma`, **et parité de la PROSE** (le nombre annoncé dans `CLAUDE.md` ×2 et dans le docblock de `tenant-extension.ts` doit valoir `SCOPED_MODELS.size`). Ces compteurs recopiés à la main avaient divergé jusqu'à afficher **trois valeurs différentes pour le même Set** (27 / 28 / 30 pour 29 modèles).
- `tests/organisation-purge-ordre.test.ts` — parité + validité topologique d'`ORDRE_SUPPRESSION`.
- `tests/roles-lists-parity.test.ts` — **aucune route ne recopie la composition de `ROLES_ARGENT`/`ROLES_BUREAU`**. Ces deux listes canoniques vivent dans `middlewares/permissions.ts` ; elles avaient été dupliquées dans 5 routes sous 3 noms (`ROLES_ARGENT` ×2, `ROLES_PAIEMENT`, `FLUX_ARGENT`, + une liste inline) et commençaient à diverger — sur les gardes d'ARGENT, une divergence silencieuse est un problème de sécurité. Test volontairement ÉTROIT : les listes légitimement distinctes (`ROLES_APPROBATION`, `['ADMIN','PRESIDENT']`…) restent permises, les commentaires sont ignorés.
- `tests/modes-versement-parity.test.ts` — parité `MODES_VERSEMENT` (`lib/modes-versement.ts`) ↔ enum Postgres `ModeVersement` (lit le schéma). Liste autrefois recopiée à la main dans 3 routes (`MODE_ENUM`/`MODES`), désormais source unique ; anti-vacant `toBeGreaterThan(0)`.
- `tests/modes-versement-source-unique.test.ts` — **complément du précédent** : la parité garde la constante ↔ enum, PAS l'absence d'une NOUVELLE recopie ailleurs. Ce test balaie tout `src/**/*.ts` (hors `generated/` et `lib/modes-versement.ts`) et échoue si un fichier reconstruit l'ensemble des modes à la main — tableau littéral, union de type, OU **table de libellés** (objet dont les CLÉS couvrent la signature `{ ESPECES: …, MOBILE_MONEY: … }`) contenant à la fois `ESPECES` ET `MOBILE_MONEY` (un `'ESPECES'` isolé comme le défaut d'`amendes.route.ts` reste permis ; une clé i18n dottée `'commun.modeVersement.ESPECES'` du catalogue n'est PAS capturée). Motif calqué sur `roles-lists-parity.test.ts`. Deux défauts vécus l'ont motivé : (1) une 4ᵉ copie (union écrite à la main dans `releve.service.ts`) hors des 3 routes, invisible du test de parité ; (2) l'angle mort de la 1ʳᵉ version — deux **tables de libellés** `Record<string,string>` par mode dans `recu-pdf.service.ts` et `releve.service.ts` (documents remis aux membres où un mode absent rendait `undefined` en silence), que la détection tableau/union ne voyait pas. **Libellés des modes = SOURCE UNIQUE dans le catalogue i18n** (`commun.modeVersement.*`), lue par `lib/i18n.ts::libelleModeVersement(mode, langue)` (repli sur la valeur brute pour un mode hérité inconnu) — ne PAS refabriquer une table de traduction dans un service.
- `frontend/src/lib/roles-parity.test.ts` — **seul garde INTER-COUCHES du dépôt** : les constantes miroir de `lib/roles.ts` (`DESIGNATION_CHEF`/`EXPORT_DONNEES`/`CONFIG_PAIEMENT`) doivent valoir le `requireRoles` de leur route serveur dans `organisations.route.ts`. Le front ne pouvant pas importer le back, rien n'empêchait mécaniquement une dérive — et les trois gardes serveur sont INDÉPENDANTES malgré leur valeur commune `['ADMIN','PRESIDENT']` (d'où trois constantes distinctes, pas une partagée). Lit les deux fichiers **en TEXTE** (jamais d'import : exécuter du code serveur dans le runner front n'aurait aucun sens), `MAPPING` route↔constante **déclaré dans le test** — le dériver en ferait une tautologie. Fragilité assumée : si une route change de forme d'appel ou déménage, l'extraction LÈVE (échec bruyant) plutôt que de passer au vert sans rien vérifier.
- **Écrire un garde de ce type = le SABOTER dans la direction utile.** Vérifier qu'il détecte un changement du fichier qu'on édite déjà prouve peu ; c'est l'autre côté qui compte (élargir un `requireRoles` SERVEUR sans toucher au miroir front, réintroduire une liste recopiée, retirer un libellé). Et **contrôler que le sabotage s'est appliqué** avant d'interpréter le résultat (assertion d'ancre dans le script + relecture de la ligne) : un sabotage qui n'a pas pris laisse un test vert qu'on croit probant.
- **Deux modes de défaillance à connaître quand on écrit ce genre de test** : (1) le test **vacant** — s'il ne trouve plus rien à inspecter (prose reformulée, `readdirSync` vide), il passe au vert sans rien assertir ; d'où une garde `expect(n).toBeGreaterThan(0)` dans chacun. (2) le **sabotage inopérant** — vérifier qu'un test échoue en cassant le code ne prouve rien si la modification n'a pas pris (ancre de remplacement absente, chemin relatif erroné) : **contrôler que le sabotage s'est appliqué** avant d'interpréter un test resté vert. Les deux se sont produits pendant l'écriture de ces gardes.
- Quand la valeur est dérivable, la DÉRIVER plutôt que la garder : le libellé du fixture de purge est `` `couverture des ${SCOPED_MODELS.size} modèles` ``, plus aucun compteur à maintenir. Même recette pour le schéma ajv des préférences de notification — `properties: Object.fromEntries(TYPES_NOTIFICATION.map(...))` (`notifications.route.ts`) : ajouter un type de notification l'ouvre AUTOMATIQUEMENT à l'API. Les listes de modes de versement, autrefois recopiées à la main (`MODES`/`MODE_ENUM`), sont désormais consolidées dans `lib/modes-versement.ts` et gardées par `tests/modes-versement-parity.test.ts` (parité constante ↔ enum Postgres, cf. § Paiement).
- **⚠️ Piège ajv/Fastify : `additionalProperties: false` ne REJETTE pas, il SUPPRIME en silence.** Avec la config ajv par défaut de Fastify (`removeAdditional`), une clé inconnue du corps est retirée et la requête répond **200** — pas 400. Défaut vécu : `REUNION_RAPPEL` ajouté aux types de notification mais absent du schéma → `PATCH /notifications/preferences` acceptait la préférence, renvoyait 200, et la **jetait**. L'utilisateur bascule l'interrupteur, l'UI confirme, rien n'est enregistré. **Un test qui n'assère que le code HTTP ne voit RIEN** : asserter l'EFFET (ce qui a été écrit), pas le statut. C'est ce qui rend la dérivation ci-dessus structurelle et non cosmétique.
