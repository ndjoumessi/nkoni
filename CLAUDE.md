# CLAUDE.md — NKONI

Gestion des cotisations & transparence financière pour associations, familles élargies et
tontines. **SaaS multi-tenant** : chaque organisation cliente a son espace isolé.

Spécifications : `NKONI_Spec_Technique_Dev.md` (mono-tenant d'origine) et
`NKONI_SaaS_Spec_Technique_v1.md` (évolution SaaS). Le code référence ces specs par section
(`§2.2`, `§3.1`, …) — garder cette convention dans les commentaires et commits.

## Structure & stack
- `backend/` — Node 20 + Fastify 5 + Prisma 7 (générateur `prisma-client` → `src/generated/prisma`, adapter `@prisma/adapter-pg`) + PostgreSQL. TypeScript, tests Vitest. Point d'entrée `src/app.ts` (`buildApp` injectable, cf. tests) ; les deux namespaces `@fastify/jwt` (access + refresh, §4.5) sont enregistrés dans `src/plugins/jwt.ts` ; seeds sous `prisma/`.
- `frontend/` — Vite + React + React Router + Tailwind v4. Design system **« Menthe & Encre »** (fintech, dark-only ; tokens oklch **centralisés dans `src/index.css`**, primitives dans `src/components/ui/`). Accent principal **menthe** (jeton `--brass`), or discret en secondaire (`--amber`), rouge/bleu pour les statuts ; fontes **Geist** (UI/titres, Fraunces retiré) + **IBM Plex Mono** pour les montants/données via la classe `.num`. Focus clavier : **un anneau menthe unique** (`:focus-visible` global). CTA primaire = dégradé diagonal émeraude → or. Un thème = édition des VALEURS de jetons (les noms restent stables : `--brass`, `--jade`, `--amber`… gardent leur rôle même après changement de teinte). **Ne pas recopier de valeurs oklch en dur** dans les composants : passer par le TOKEN (`var(--brass|jade|hairline)`) + `color-mix(in oklch, …)` pour l'alpha (cf. `EmptyState`, `RecouvrementHero`, `ErrorState`). **États d'erreur de page** = primitive partagée `ui/ErrorState.tsx` (miroir d'`EmptyState` en tons `--terra`, `role="alert"`, bouton « Réessayer » optionnel) — ne pas redupliquer. `ui/Modal.tsx` embarque un **piège de focus** complet (mémorise le déclencheur, boucle Tab/Shift+Tab, restaure au close). **DEUX couches de jetons, et le sens de la dépendance compte** : `src/index.css` importe `shadcn/tailwind.css` (ligne 3) et **remappe les jetons shadcn SUR les nôtres** (`--primary: var(--brass)`, `--background: var(--canvas)`, `--card: var(--surface)`…). La source de vérité est donc la couche NKONI (`--canvas`/`--surface`/`--brass`/`--jade`…) ; la couche shadcn en DÉRIVE. Rethématiser = éditer les valeurs NKONI, jamais les `--primary`/`--background` qui se recalculent tout seuls. (Les blocs `/* Jetons shadcn (remappés Laiton & Jade) */` portent encore l'ANCIEN nom de palette — les noms de jetons sont volontairement stables, cf. ci-dessus, seules les valeurs ont changé.) **`shadcn` est une dépendance VIVANTE, consommée par un `@import` CSS et non par du JS** : chercher ses imports dans les `.tsx` ne rend rien et ferait conclure à tort qu'elle est morte — la retirer casserait tout le remap. (`@base-ui/react`, elle, était réellement orpheline — zéro référence dans TOUT le dépôt — et a été retirée ; le bundle n'a pas bougé d'un octet, preuve qu'elle n'y entrait pas.) **Vérifier une dépendance « morte » = grep sur le dépôt ENTIER (CSS et configs compris), pas sur `src/**.tsx`.**
**Logo** : `components/ui/NkoniMark.tsx` = SVG « Cercle d'union » (membres menthe autour de la cagnotte émeraude→or, chef en or), réutilisé partout ; `public/favicon.svg` porte le MÊME design et les **icônes PNG PWA** (`public/pwa-*.png`) en sont dérivées — à **régénérer** via `rsvg-convert` (tuile `#0f1512`) à tout changement de logo, sinon elles restent périmées.

## Architecture — points essentiels

**Isolation multi-tenant (SaaS §2.2)** — défense en profondeur, `backend/src/lib/` :
- `org-context.ts` : `AsyncLocalStorage` portant l'`organisationId` de la requête. `runUnscoped()` = bypass DÉLIBÉRÉ pour les flux sans org (login/refresh/système/seed/super-admin). **Allowlist source (audit archi)** : `tests/runUnscoped-allowlist.test.ts` énumère TOUS les appels `runUnscoped` du `src/` (hors `generated/`) et exige une parité stricte avec une liste justifiée (par fichier + compte) — tout nouvel appel casse le build tant qu'un relecteur ne l'a pas inscrit et justifié (les commentaires ne sont pas un garde-fou exécutable). Pendant côté APPELANTS du test de parité `SCOPED_MODELS ↔ schéma`.
- `tenant-extension.ts` : extension Prisma `$extends` qui injecte `organisationId` sur les 34 `SCOPED_MODELS` (dont `Depense`, `CagnotteEvenement`, `DonCagnotte`, `Amende`, `ParametrePaiement`, `Paiement`, `PresenceReunion`, `Vote`, `Tontine`, `CycleTontine`, `ParticipationTontine`, `TourTontine`, `MiseTontine`). **Fail-closed** : sur un modèle scopé sans contexte org valide → lève `TenantContextError` ; une opération scopée NON couverte par l'extension (ex. `createManyAndReturn`) → lève `OperationNonIsoleeError` (jamais de passe-plat silencieux). **`aggregate` et `groupBy` SONT couverts** (`READ_WHERE_OPS`, avec `findMany`/`findFirst[OrThrow]`/`count`) : agréger côté Postgres sur un modèle scopé est SÛR et reste la voie normale — ne pas rapatrier les lignes pour les sommer en JS « par prudence d'isolation », cette prudence n'a pas d'objet (défaut réel, corrigé dans `/moi/cagnottes` : un commentaire affirmait l'inverse alors que la route sœur `GET /cagnottes` agrégeait déjà `donCagnotte` par `groupBy` en production). Mutation cross-org → `P2025` (→ 404, pas de fuite d'existence).
- `Organisation` n'est **PAS** un modèle scopé (les routes plateforme la lisent sans contexte).
- Ordre des extensions (`lib/prisma.ts`) : audit puis tenant (tenant outermost → scope/fail-close AVANT l'audit).
- **`findUnique[OrThrow]` + `select` : l'extension gère la troncature.** Le contrôle d'appartenance est un POST-filtre sur `res.organisationId`. Si l'appelant fournit un `select` qui **omet** `organisationId`, l'extension l'ajoute le temps de la requête puis le **retire** du résultat rendu (sinon `undefined !== orgId` → faux « introuvable » sur TOUTE ligne, y compris la sienne). Donc un `select` n'a pas à inclure `organisationId` — mais si tu écris un post-filtre analogue ailleurs, souviens-toi que Prisma ne renvoie que les champs sélectionnés. Couvert par `tests/tenant-findunique-select.test.ts` + repro d'intégration.
- **Écritures scopées = FK SCALAIRES (input « unchecked »), jamais la forme relation `{ connect }`.** L'extension force le **scalaire** `organisationId` dans le `data` d'un `create`/`createMany`. Utiliser une relation pour une AUTRE FK (ex. `televersePar: { connect: { id } }`) bascule Prisma en input « checked », où `organisationId` scalaire n'existe pas et la relation `organisation` devient obligatoire → « Argument `organisation` is missing ». Écrire les FK en scalaire (`televerseParId: id`, cast `…UncheckedCreateInput`) comme tous les creates scopés. Régression : `tests/document-create.integration.test.ts`.

**Rôles & permissions** — `backend/src/middlewares/permissions.ts` :
- Matrice `PERMISSIONS[entité][rôle]` + `requirePermission(entité, action)`. Miroir front dans `frontend/src/lib/roles.ts`.
- Entité `Organisation` (paramètres de l'org, **lecture seule**) : ouverte à tous les rôles d'organisation **sauf** MEMBRE_SIMPLE (le quota relève de la gestion). `GET /organisations/moi` (scopé, self-service) renvoie nom/devise/langue défaut/date + le **forfait** courant + **nb de membres ACTIFS vs limite du forfait** (`limiteMembres` = `null` si illimité) + le **chef** (`chefMembreId`/`chefSurnom` + nom/prénom) ; écran `/parametres` (lecture seule, ces paramètres sont **immuables** §5, chef inclus en affichage). Le SUPER_ADMIN reste hors matrice → 403.

**Forfaits (SaaS §3.1)** — enum `Forfait` (`GRATUIT`/`PRO`/`ENTREPRISE`) + champ `Organisation.forfait @default(GRATUIT)` (migration `forfait_organisation`, colonne NOT NULL DEFAULT → backfill implicite). Source de vérité PARTAGÉE `backend/src/lib/forfait.ts` (+ miroir `frontend/src/lib/forfait.ts`) : `limiteMembresForfait(forfait)` → **GRATUIT = 50**, **PRO/ENTREPRISE = `null` (illimité)**. Le quota membres (POST `/membres`, `/membres/import`) lit le forfait de l'org et n'applique le plafond QUE si non `null`. **Attribution = action PLATEFORME manuelle réservée au SUPER_ADMIN** (pas de paiement) : `PATCH /platform/organisations/:id/forfait` (garde `requireSuperAdmin`, `runUnscoped`, 404 sur id inconnu) ; console super-admin = sélecteur de forfait par org (MAJ optimiste). Libellés i18n partagés `commun.forfaits.{GRATUIT,PRO,ENTREPRISE}`.
- **Chef de l'organisation** — SEULE écriture sur `Organisation` : `PATCH /organisations/moi/chef` (désigne/retire un Membre dirigeant + surnom). C'est une **action mutable HORS matrice** (les paramètres §5 restent immuables), gardée par **`requireRoles(['ADMIN','PRESIDENT'])`** (`middlewares/permissions.ts`, factory réutilisable façon `requireSuperAdmin` — à préférer à un `requirePermission('Organisation','update')` qui laisserait croire les paramètres modifiables). Le membre est validé par une lecture **scopée** (`membre.findUnique` → un membre d'une autre org renvoie `null` → 404, isolation tenant) ; l'écriture cible `Organisation` (modèle NON scopé) par id en **FK SCALAIRE** (`chefMembreId`, jamais `{ connect }`). Schéma : FK `onDelete: SetNull` (migration additive `chef_organisation`). Front : désignation depuis la fiche membre (ADMIN/PRESIDENT), badge « Chef » sur liste/fiche, affichage lecture seule sur `/parametres`. `peutDesignerChef` miroir dans `lib/roles.ts`.
- `authenticate` (hook JWT) peuple `req.user` et appelle `orgContext.setOrganisation(req.user.organisationId)`.
- **SUPER_ADMIN** (rôle plateforme transverse, §2.3) : `organisationId` NULL (invariant CHECK en base), **absent de la matrice** → 403 sur toute route tenant. Ses seules routes : `/platform/*` (garde `requireSuperAdmin`). Voir la mémoire `nkoni-super-admin`.

**Auth (§4.5)** — JWT access (Bearer, en mémoire côté front) + refresh (cookie httpOnly, namespace `@fastify/jwt` séparé). Émission factorisée dans `lib/session.ts` (partagée login + auto-inscription). argon2 pour les mots de passe.
- **Révocation de session par époque (audit M5)** — `Utilisateur.sessionEpoch Int @default(0)` (migration `session_epoch`, sans backfill). Le refresh token porte le claim `epoch` = `sessionEpoch` à l'émission (`session.ts`) ; `POST /auth/refresh` rejette (401) si `(payload.epoch ?? 0) !== user.sessionEpoch`. `changerMotDePasse` (self) et `reinitialiserMotDePasse` (admin) **incrémentent** `sessionEpoch` → **toutes les autres sessions tombent au prochain refresh** (TTL access 15 min). **Rétro-compatible** : un refresh token émis AVANT la feature n'a pas de claim `epoch` → traité comme `0`, donc valide tant que l'utilisateur n'a pas changé son mot de passe (pas de déconnexion de masse au déploiement). Le changement de mot de passe réémet une session fraîche à l'appelant.
- **Rotation des refresh tokens + détection de réutilisation (audit M5)** — refresh tokens **STATEFUL** : modèle `RefreshToken` (migration `refresh_token`) `{ jti unique, utilisateurId, familleId, revoke, expiresAt }`, **NON scopé** (pas d'`organisationId` → accès en `runUnscoped`/direct, hors `SCOPED_MODELS`, parité `tests/tenant-scoped-models.test.ts` préservée). Chaque refresh porte `jti` (identité) + `fam` (famille, constante sur toute une chaîne de rotations issue d'un même login) + `rem` (propage le `rememberMe` à travers les rotations — sans quoi un « se souvenir de moi » retomberait à 7 j au 1ᵉʳ refresh). `emettreSession(reply, user, rememberMe, { prisma, familleId? })` **persiste** le token si `prisma` est fourni (login, inscription, refresh, reset MDP) ; `familleId` fourni = **reste dans la même famille** (rotation), sinon neuve. `POST /auth/refresh` : si `jti` présent → lit le `RefreshToken` (absent/expiré → 401), sinon **`revoke === true` = replay d'un token volé → révoque TOUTE la famille (`updateMany`)** + 401 ; sinon **révoque ce `jti` et réémet dans la même famille** (rotation). Un refresh **legacy** (émis avant la feature, **sans `jti`**) est accepté une fois puis **migré** vers stateful (rétro-compat, pas de déconnexion de masse au déploiement). `POST /auth/logout` révoque désormais **la famille côté serveur** (best-effort : cookie effacé même si le refresh est absent/illisible) — déconnexion réelle, plus un simple `clearCookie`. Complète (n'annule pas) la **révocation par époque** ci-dessus : l'époque coupe TOUTES les sessions au changement de MDP, la rotation coupe UNE chaîne compromise sur replay.

**Sécurité HTTP (audit W)** — `app.ts` : **`trustProxy: true` est OBLIGATOIRE** (derrière Railway/Vercel l'IP client réelle est dans `X-Forwarded-For` ; sans ça `@fastify/rate-limit` keyerait sur l'IP du proxy = **un seul seau pour tous → lockout global**). `@fastify/rate-limit` global `max: 300`/`1 minute` (surcharge par route via `config.rateLimit`). `@fastify/helmet` avec `crossOriginResourcePolicy` assoupli (proxy same-origin Vercel). `lib/env.ts` : fail-fast sur les secrets OBLIGATOIRES (`JWT_*`) au démarrage + **warnings prod NON bloquants** (audit W1, muets hors prod) si `CORS_ORIGIN`/`RECU_LINK_SECRET`/`BLOB_READ_WRITE_TOKEN` retombent sur leur défaut risqué.

**Audit trail (V2 §5)** — `lib/audit-middleware.ts`, extension Prisma, 6 entités. Best-effort (n'échoue jamais l'op métier), `passwordHash` toujours exclu, sauté pour les écritures non scopées (`runUnscoped`).

**Observabilité (bloquant GA 0.1, audit M7)** — `lib/observabilite.ts` (+ miroir front `frontend/src/lib/observabilite.ts`) : client **`ObservabiliteClient` MOCKABLE**, injectable via `buildApp({ observabilite })` comme `blob`/`whatsapp`, **inerte sans `SENTRY_DSN`** (front : `VITE_SENTRY_DSN`). **Une COUCHE, pas un `Sentry.captureException` dispersé** : c'est ce qui rend les points d'alerte ASSERTABLES (on injecte un espion et on vérifie qu'ils signalent — `tests/observabilite.test.ts`), et qui tient la règle « ne jamais faire échouer l'opération métier » à UN endroit. **Les `log.error`/`console.error` existants RESTENT** : les logs Railway doivent suffire à diagnostiquer même Sentry absent ou en panne — l'observabilité AJOUTE l'alerte, elle ne remplace pas la journalisation. Trois points câblés, choisis parce qu'ils étaient **aveugles** : (1) les **5xx** du gestionnaire d'erreur `app.ts` (contexte = **motif de route** `req.routeOptions.url`, pas l'URL réelle → pas d'identifiant dans un titre d'incident, et regroupement correct) ; (2) l'**échec d'écriture d'audit** — c'était un `console.error` que personne ne lisait, alors qu'une écriture métier NON tracée est un incident sur un produit de transparence financière (l'opération a réussi, la preuve manque) ; (3) l'**échec du scheduler nocturne** — silencieux par nature (personne n'attend sa sortie à 03:00), il pouvait échouer toutes les nuits sans que les relances cessent d'être remarquées. L'extension d'audit étant construite au chargement du module (`lib/prisma.ts`, pas d'instance Fastify sous la main), son injection se fait **par paramètre** de `intercepterAudit`, pas par décoration. **Côté front, le tri du bruit est la pièce qui compte** (`estIncidentDigneDAlerte`) : sur une PWA en mobilité, un `ApiError` < 500 (refus métier, validation, 401) et un `fetch` coupé sont ATTENDUS — les remonter noierait les vrais incidents ; seules les 5xx et les erreurs non réseau (bugs de rendu) alertent. Le SDK front est en **`import()` dynamique** gardé par le DSN → sans configuration, le chunk (~475 kB) n'est jamais téléchargé (vérifié : aucun `modulepreload` dans `index.html`). `sendDefaultPii: false` et pas de tracing des deux côtés (on cherche l'alerte, pas le profilage ; et les corps de requête portent téléphones, noms et mots de passe). `lib/env.ts` avertit en prod si `SENTRY_DSN` manque (même famille que les warnings W1). **`ErrorBoundary` applicatif** (`frontend/src/components/ErrorBoundary.tsx`, monté au sommet de l'arbre dans `main.tsx` → couvre routeur, providers et pages) : le `window.onerror` global ALERTAIT déjà une erreur de rendu, mais laissait un **écran blanc** — l'alerte n'est pas l'écran. Le boundary capte le crash, signale par la MÊME couche `observabilite` et affiche un fallback lisible. Deux contraintes de structure : un error boundary n'existe qu'en **composant classe**, donc il ne peut appeler aucun hook → le fallback est un composant fonctionnel SÉPARÉ qui porte `useTranslation` et réutilise la primitive `ui/ErrorState` (pas de style redupliqué) ; et la reprise est un **rechargement dur** (`window.location.reload()`), pas une navigation routeur qui re-crasherait sur l'état corrompu.

**Bannière d'incident / page de statut (§2.2/§8)** — `services/statut-incident.service.ts` + `routes/statut.route.ts`, modèle `StatutIncident` **PLATEFORME NON scopé** en **singleton** (`id = 'singleton'`, upsert — un incident concerne tout le service, pas un tenant ; donc aucun `runUnscoped` ni contexte org, l'extension d'isolation le laisse passer). Gravités `INFO`/`MAINTENANCE`/`INCIDENT`, message borné à 500 caractères (c'est un bandeau). **Trois routes, et l'asymétrie entre les deux GET est le point** : `GET /statut/incident` est **PUBLIC** et ne révèle le message QUE si la bannière est `actif` (sinon `{ actif: false }` — rien à divulguer tant qu'on n'a pas publié) ; `GET /platform/statut/incident` (SUPER_ADMIN) renvoie l'état **COMPLET**, message inclus même inactif, pour pré-remplir l'éditeur — on rédige d'abord, on bascule `actif` ensuite ; `PUT /platform/statut/incident` (SUPER_ADMIN) fait l'upsert. Front : `pages/StatutPage.tsx`, qui sonde `/ready` pour l'état technique (cf. `/health` vs `/ready` plus bas) et cette route pour le message humain. C'est le levier de communication du RUNBOOK incidents.

**Export & suppression définitive d'un tenant (bloquant GA 0.3)** — `services/organisation-purge.service.ts` + 2 routes plateforme (`platform.route.ts`, garde `requireSuperAdmin`) : `GET /platform/organisations/:id/export` (lecture seule, idempotent) et `DELETE /platform/organisations/:id`. **DOUBLE VERROU** sur la suppression : organisation **déjà suspendue** (`actif = false`, 409 sinon) **et** `confirmationNom` égal EXACTEMENT au nom (400 sinon, motif « frappez le nom du dépôt » de GitHub) — un DELETE par UUID nu n'offre aucune marge sur une erreur d'identifiant, et l'opération ne se rattrape pas. La précondition de suspension n'est PAS administrative mais **technique** : le scheduler ne balaie que les orgs `actif: true` et l'auth refuse login/refresh sur un espace inactif, donc c'est elle qui garantit qu'aucun écrivain concurrent n'entre en conflit avec la transaction (la relire DANS la transaction, sinon un `/reactiver` concurrent passe entre les gouttes).
- **`ORDRE_SUPPRESSION` est FIGÉ, pas dérivé** — un tri topologique du DMMF raterait `Document.entiteId` (référence POLYMORPHE, invisible du graphe) et **omettrait `RefreshToken`** (ni FK ni `organisationId` : rattaché à rien, c'est LE modèle dont l'oubli laisse des sessions vivantes après purge — ses `utilisateurId` doivent être collectés AVANT la suppression des `Utilisateur`). Deux tests gardent la liste (`tests/organisation-purge-ordre.test.ts`) : **parité** avec `SCOPED_MODELS ∪ {RefreshToken, Organisation}` et **validité topologique** dérivée du schéma (toute arête `onDelete: Restrict` enfant→parent respectée) — ce dernier tombe tout seul si une migration transforme un `SetNull` en `Restrict`. Seules les FK `Restrict` contraignent l'ordre ; `Membre.chefSousFamilleId` est en `SetNull` (vérifié en base), donc l'auto-relation ne pose rien.
- **Chaque `deleteMany` porte `where.organisationId`, construit par le service et jamais par l'appelant.** La purge tourne sous `runUnscoped` (le SUPER_ADMIN n'a pas d'org) donc **l'extension d'isolation est NEUTRALISÉE** : un `deleteMany({})` sur `Membre` effacerait TOUTES les organisations sans lever la moindre erreur. On supprime la classe d'erreur au lieu de la tester. Rester en `deleteMany` est aussi ce qui évite l'audit (`OPERATIONS_AUDITEES` = create/update/delete unitaires) — une boucle de `delete` réécrirait dans `AuditLog` pendant qu'on le vide.
- **Base d'abord, blobs ENSUITE** — contre-intuitif (les pathnames Blob ne sont **pas** préfixés par organisation, les photos vont toutes sous le littéral `membres/photo`, et `BlobClient` n'a pas de `list()` : la base est la seule source d'appartenance tenant→fichier), mais strictement meilleur **parce que l'export capture les URLs d'abord**. Filet de sécurité : `GET /tresorerie/reconciliation` (`reconcilierVersements`) compare, membre par membre, la somme des versements aux cumuls stockés et renvoie les **écarts** — endpoint auth-gated de contrôle, pas d'écriture.
- **Ouvrir une année : GLOBALE vs CIBLÉE.** Le montant attendu d'un membre est **calculé** sur sa fenêtre `[anneeAdhesion .. min(anneeCourante, anneeFinContribution)]` × barèmes, alors qu'**encaisser** exige une ligne `Contribution`. Ces deux vérités divergent dès qu'une année de la fenêtre n'a jamais été ouverte : l'app comptait l'année comme attendue mais le formulaire de versement ne la proposait pas (bug vécu, membre adhérent 2023 encaissable seulement sur 2025-2026). D'où deux opérations : `ouvrirAnnee(annee)` = **toute l'organisation** (`createMany skipDuplicates`, ADMIN/TRESORIERE) et `ouvrirAnneeMembre(membreId, annee)` = **un seul membre** (`POST /contributions/ouvrir-membre`), **idempotent** (renvoie l'existante), mêmes règles : barème OBLIGATOIRE (`montantAttendu` copié → historisation, jamais de création à 0), éligibilité (ACTIF + fenêtre), `null` → 404 sans fuite d'existence, création en **FK scalaire**. Côté front, le sélecteur d'année du versement couvre **toute la fenêtre** (pas les seules années ouvertes) et ouvre à la volée l'année choisie avant d'encaisser ; arrivé par « + Versement » depuis la ligne d'une année, l'année est **verrouillée** (contexte, pas choix — déverrouillable). L'ouverture **GLOBALE** se déclenche depuis la page **Barème** (et non le formulaire de versement, où elle ferait doublon avec l'ouverture ciblée automatique) : elle y prolonge la configuration du barème de l'année, et son bouton est désactivé tant que l'année n'a pas de barème. **Garde-fous page Barème** : l'ajout d'une année **déjà configurée** est bloqué en amont (409 évité, champ visé sur la 1ʳᵉ année LIBRE + réarmé après chaque ajout, message « utilisez Modifier ») ; une ré-ouverture **sans effet** (0 contribution créée, l'opération étant idempotente) affiche un toast **INFO « Rien à créer »** au lieu d'un faux succès vert (ré-ouvrir reste utile pour les membres ajoutés APRÈS la 1ʳᵉ ouverture). **Borne haute = jamais d'année FUTURE** (`AnneeFutureError` → 400 i18n, sur les DEUX opérations) : la fenêtre d'attendu s'arrêtant à `min(anneeCourante, …)`, une contribution ouverte en avance serait affichée et encaissable alors que les totaux du membre l'ignorent — l'argent reçu deviendrait invisible. Trois corollaires : la borne est placée **APRÈS la lecture idempotente** (une contribution future déjà créée reste consultable/encaissable, le correctif ne séquestre pas d'argent déjà encaissé) ; configurer le **barème** d'une année future reste PERMIS (seule son ouverture attend l'échéance) ; côté page Barème le défaut du sélecteur vise la dernière année de barème **ÉCHUE** (viser le max absolu proposait l'année future dès qu'un barème était configuré en avance). `anneeCourante` est **injectable** dans les deux fonctions, son défaut passant par `anneeCouranteApp()` (cf. fuseau applicatif).
- **Pagination par offset (audit m4)** — helper PARTAGÉ `backend/src/lib/pagination.ts` (`resoudrePagination` borne page/pageSize : défaut 25, max 100 ; `PAGINATION_PROPS` = fragment ajv à fusionner dans la querystring ; réponse stable `PageResultat<T> = { items, total, page, pageSize }`) pour les listes qui grandissent sans limite (dépenses paginées d'abord). Miroir front `frontend/src/components/ui/Pagination.tsx` + `Paginated<T>` dans `lib/api.ts` — **réutiliser, ne pas réinventer** un schéma de pagination ad hoc.
  - **`/membres/statuts` = réponse BORNÉE, pas offset (audit m4)** — le statut de cotisation est **calculé** (borne d'années × barèmes, pas une colonne DB), donc une vraie pagination offset exigerait de matérialiser le statut (reporté, aucun besoin). À la place `calculerStatutsMembres(prisma, annee, where?, limite?)` (`services/membreStatut.service.ts`) renvoie `{ items, total, tronque }` et **borne à `PLAFOND_STATUTS_MEMBRES = 1000`** ; `tronque = total > limite`. Côté front, `membresApi.listStatutsPage` expose l'objet (bannière de troncature sur `MembresPage`) tandis que `membresApi.listStatuts` **déballe `.items`** pour les nombreux appelants « tableau seul » (sélecteurs, dashboard, ⌘K). Les consommateurs de `calculerStatutsMembres` (cartes, relevé) déstructurent `.items`.

**Réunions & votes en ligne (§ vie associative)** — au-delà du CRUD réunions/ordre du jour/résolutions (`reunions.route.ts`, `resolution.service.ts` — résolutions **purement documentaires**, aucun effet mécanique), trois sous-systèmes ajoutés :
- **RSVP / présences** — `PresenceReunion` (scopé, `@@unique([reunionId, membreId])`). Le membre pose SON intention en self-service (`PUT /moi/reunions/:id/rsvp`, résolu par `req.user.sub`, hors matrice comme tout `/moi/*`) ; un dirigeant l'ajuste (`GET`/`PUT /reunions/:id/presences/:membreId`, matrice `Reunion`/read|update). `GET /moi/reunions` fusionne `monStatut`.
- **Rappel de réunion** — type de notification `REUNION_RAPPEL` (cf. Scheduler) : la tâche de nuit prévient chaque membre ACTIF à compte lié des réunions à venir sous 48 h, **une fois par réunion et par membre** (dédoublonné sur `entiteId`, sinon le cron quotidien × fenêtre 48 h rappellerait deux nuits). Désactivable par préférence.
- **Compte-rendu PDF** — `GET /reunions/:id/compte-rendu.pdf` (`compte-rendu-pdf.service.ts`, réutilise `export-style.ts`). **Régénéré à la volée, JAMAIS stocké** (contrairement au reçu, idempotent sur Blob) : le compte-rendu est mutable, un PDF caché mentirait.
- **Votes en ligne** — modèle `Vote` (scopé, `@@unique([resolutionId, membreId])` → revoter écrase). `vote.service.ts` + `votes.route.ts`. **Trois décisions non déductibles du code, à NE PAS « harmoniser » :**
  1. **Mise au vote EXPLICITE + clôture, SANS nouvel enum** : `StatutResolution` ne porte pas d'état « en vote ». Deux booléens/dates portent le cycle : `Resolution.ouvertAuVote` (défaut **false**) et `dateVote`. « En vote » = **`ouvertAuVote === true && dateVote === null`**. Un dirigeant ouvre le scrutin (`POST /resolutions/:id/ouvrir-vote`) ; le membre vote alors (`PUT /moi/resolutions/:id/vote`, refus `ResolutionNonOuverteError` → 409 si non ouverte, `ResolutionClotureeError` → 409 si clôturée) ; la clôture pose `dateVote`. **Le défaut `ouvertAuVote: false` est le garde-fou clé** : une résolution documentaire (résultat déjà acté) n'apparaît JAMAIS dans « Votes en cours » (`GET /moi/resolutions` filtre `ouvertAuVote: true, dateVote: null`) et ne peut pas être clôturée-par-vote — sinon un vote fortuit écraserait son statut historique à la clôture. `cloturerResolution` exige donc aussi `ouvertAuVote`.
  2. **Le dépouillement est NOMINATIF et gardé HORS matrice** : `GET /resolutions/:id/votes` est gardé par **`requireRoles(ROLES_BUREAU)`**, PAS par `requirePermission('Reunion','read')` — la matrice `read` inclut MEMBRE_SIMPLE, ce qui exposerait à tout membre qui a voté quoi (sur un conflit, une exclusion, de l'argent). C'est délibéré : « harmoniser » cette garde avec le reste des routes réunion rouvrirait la fuite. Verrouillé par `votes.route.test.ts` (MEMBRE_SIMPLE → 403). La **clôture** (`POST /resolutions/:id/cloturer`) reste sur `Reunion`/update (ADMIN/PRESIDENT/SECRETAIRE), déjà plus restrictif que le bureau. **Deux gardes ⇒ deux miroirs front distincts** (`lib/roles.ts`) : `peutDepouillerVotes` (bureau, miroir de `ROLES_BUREAU`) pour le tally, `peutGererReunions` (gestion) pour la clôture — les confondre masquerait le dépouillement à la trésorière et au commissaire aux comptes, que le serveur autorise pourtant.
  3. **Statut DÉRIVÉ du tally** (`statutSelonTally`, pur) : POUR **strictement** > CONTRE → ADOPTEE, sinon REJETEE (égalité et 0-0 incluses). Les ABSTENTION ne comptent pas dans la majorité ; `REPORTEE` n'est jamais automatique. Quorum/majorité qualifiée = à ajouter ICI si besoin.
  - **Garde d'appartenance dans le SERVICE, pas la route** : `voterResolution` revérifie `membreId` par une lecture SCOPÉE (→ `MembreIntrouvableError` → 404), car sur un `upsert` dont la cible n'existe pas l'extension tenant force `organisationId` dans le `create` mais laisse passer les autres FK — un `membreId` d'une autre org créerait un `Vote` de l'org courante pointant vers un membre étranger. Non exploitable par la route actuelle (membre résolu par `sub`), la garde protège le prochain appelant. `ROLES_BUREAU` vit dans `middlewares/permissions.ts` (remonté depuis `cartes.route.ts` — une seule source, pas deux copies).

**Tontine — épargne rotative / ROSCA (§ tontine)** — `Tontine` → `CycleTontine` (rotation complète) → `TourTontine` (un bénéficiaire par tour) ; `ParticipationTontine` (membre ↔ cycle, `parts` + `ordre`) et `MiseTontine` (versement d'un participant pour un tour). 5 modèles scopés, `services/tontine.service.ts` + `routes/tontines.route.ts`, front `pages/Tontines{,Detail}Page.tsx`. **Cinq décisions non déductibles du code :**
- **ADOSSEMENT AUTONOME — la tontine est HORS `GET /tresorerie`, délibérément.** Elle fait circuler l'argent des MEMBRES entre eux (Σ mises collectées = pot reversé, net ≈ 0) ; ce n'est pas la trésorerie de l'association. L'inclure dans `calculerTresorerie` fausserait le solde en le gonflant d'un argent qui n'appartient pas à l'organisation et qui ressort intégralement. Les agrégats tontine vivent dans les vues tontine. **Ne pas « unifier » avec la trésorerie.**
- **`ENCHERE` est schema-ready mais NON câblé** : `ouvrirCycle` l'accepte, aucun bénéficiaire n'est assigné automatiquement et `tirerBeneficiaire` le REFUSE (`ModeNonSupporteError` → 409). Le front l'offre à la création mais n'affiche aucune UI d'attribution (« à venir »). Sa logique (mise à prix, escompte) s'implémente dans le service, pas ailleurs.
- **Deux rotations, deux moments** : `ORDRE_FIXE` assigne TOUS les bénéficiaires **à l'ouverture** du cycle (tour k → participant d'ordre k) ; `TIRAGE` attribue **tour par tour**, parmi ceux qui n'ont pas encore reçu. Le tirage utilise **`randomInt` (CSPRNG), jamais `Math.random`** : il décide qui touche le pot, et recevoir tôt vaut strictement mieux que tard (valeur temporelle + risque d'effondrement du cycle, où les derniers cotisent sans recevoir). Le sélecteur d'index reste injectable **pour les tests uniquement** — pas de repli non sûr par défaut.
- **Séparation gestion/argent** (même pattern que Cagnottes/Amendes) : la CONFIGURATION (créer, ouvrir un cycle, tirer) passe par la matrice `requirePermission('Tontine', …)` ; les FLUX D'ARGENT (mise, reversement) sont gardés à part par **`requireRoles(ROLES_ARGENT)`**. Miroirs front DISTINCTS dans `lib/roles.ts` (`peutGererTontines` vs `peutFluxArgentTontine`) — les confondre donnerait au SECRETAIRE des boutons qui répondent 403.
- **Garde d'appartenance des participants DANS le service** : `ouvrirCycle` revérifie chaque `membreId` par une lecture SCOPÉE (`MembreIntrouvableError` → 404). L'extension tenant ne rattrape PAS ce cas — elle force `organisationId` sur le `create` mais laisse les autres FK, et la clé étrangère vers `Membre` est satisfaite quelle que soit l'org. Les `membreId` venant du CORPS de la requête, un membre d'une AUTRE organisation serait entré dans le cycle et, en ORDRE_FIXE, serait devenu **bénéficiaire du pot**.
- **Suivi de collecte** : `getTontine` inclut les **mises par tour** (`tours.mises` = `{ membreId, montant }`). Le front en dérive, par tour non reversé, le **collecté à ce jour** (`Σ mises`) face au **pot ATTENDU** (Σ parts × `montantBaseMise`, calculé client) + une **checklist payé/non-payé par participant** — la vue du trésorier. Une fois le tour reversé, on affiche le `montantPot` RÉEL figé par le serveur. Les mises ne sont pas incluses dans les autres lectures (liste), seulement dans le détail.

**Espace membre `/moi/*` (§5)** — surface SELF-SERVICE (`routes/moi.route.ts`, + `moi-photo`/`moi-avatar`), front `pages/MonEspacePage.tsx`. Trois invariants gouvernent TOUTE nouvelle route `/moi/*` :
- **Le sujet est résolu par `req.user.sub`, JAMAIS par un id d'URL** → la classe IDOR est supprimée **par construction**, pas par une garde qu'on pourrait oublier. Ces routes sont donc **hors matrice** (comme `/auth/me`), et le `where { membreId }` est ce qui isole — à ASSERTER dans le test, c'est le seul verrou.
- **Elles n'ouvrent AUCUN chemin d'écriture métier.** Le membre VOIT ; le bureau ENREGISTRE (mise de tontine, encaissement d'amende, don). Exceptions volontaires et self-service pures : RSVP, vote, photo/avatar, démarrage de paiement.
- **Elles n'élargissent PAS la matrice** : `Cagnotte`/`Amende`/`Tontine` accordent déjà `READ` à `MEMBRE_SIMPLE`, ces vues sont strictement plus étroites (ses lignes, ou des agrégats). Vérifier ce point avant d'ajouter une vue — si la matrice refusait la lecture, `/moi/*` ne doit pas la contourner (cf. le dépouillement nominatif des votes, délibérément réservé au bureau).
- Sans fiche membre (compte purement administratif) : les **listes rendent `[]`**, seul `/moi/situation` fait un 404 propre. Ne pas transformer ça en 404 partout — un ADMIN sans fiche est un cas NORMAL.
- **Vues membre tontines / amendes / cagnottes** — deux décisions non déductibles : (1) **`maMisePayee` = Σ de MES mises **≥** la mise due** (`parts × montantBaseMise`), pas « une mise existe » — un versement partiel de 2 000 sur 10 000 ne doit pas s'afficher « payé » ; le champ `monMontantMise` accompagne le booléen pour que le front distingue *partiel* de *non commencé*. Ne pas « simplifier » en `mises.length > 0`. (2) **`collecteTotal` est COLLECTIF** (Σ des dons de tous, transparence assumée) tandis que `monDon` est le filtre personnel : ce sont **deux `groupBy`**, et c'est le `where` du SECOND qui porte `membreId` — l'omettre rendrait la collecte de tout le monde comme don personnel, avec un montant plausible donc invisible à la relecture (assertion dédiée dans `tests/moi.route.test.ts`).

**Paiement en ligne / PSP — multi-provider (§ paiement)** — les membres règlent leurs cotisations par Mobile Money ; l'argent va **DIRECTEMENT** sur le compte du prestataire de l'organisation (NKONI n'est **jamais** custodian — il orchestre la collecte et la trace). Abstraction `PspClient` (`backend/src/services/psp.service.ts`) : interface **MOCKABLE** (`initierCollecte`/`verifierStatut`/`verifierSignatureWebhook`) injectée dans `buildApp` comme `blob`/`whatsapp`/`email` ; `pspMock` inerte pour les tests. Le cœur métier ne connaît QUE l'interface — le choix du PSP est un détail porté par les `creds` de CHAQUE appel, **jamais un état global**.
- **Dispatcher multi-provider** (`lib/psp-registry.ts`) : implémente `PspClient` en routant chaque appel vers l'adaptateur de `creds.provider` (`ADAPTATEURS = { FAPSHI, CAMPAY }`). C'est LUI qu'injecte `buildApp` par défaut (`app.psp`). Ajouter un PSP = un adaptateur de plus, rien d'autre à toucher ; `paiement.service`/routes restent provider-agnostiques.
- **Adaptateurs** : `lib/psp-fapshi.ts` = **checkout HÉBERGÉ** (`/initiate-pay` → lien de redirection ; en-têtes `apiuser`/`apikey` ; base `sandbox`/`live` ; le numéro est collecté sur la page Fapshi). `lib/psp-campay.ts` = **collecte DIRECTE** (le numéro `from` du payeur déclenche une invite MoMo sur son téléphone, **pas de redirection** ; auth `username`+`password` → POST `/token/` pour un token temporaire, **repli** jeton permanent `token` ; base `demo`/`www` ; `amount` en **chaîne**, `from` E.164 sans `+`). Les deux mappent le statut PSP → `REUSSI/ECHEC/EN_ATTENTE/EXPIRE` (défaut prudent **EN_ATTENTE** sur inconnu/erreur réseau — on ne tranche jamais à tort) et **remontent le corps de réponse dans leurs erreurs** (`CamPay collect 400 — …` : fini le vol en aveugle, c'est ce qui a permis de diagnostiquer `ER201` « max 25 XAF » en demo).
- **Config PAR ORG** (`ParametrePaiement`, 1 ligne/org, `organisationId @unique`) : identifiants du PSP = **secrets de TIERS** chiffrés AES-256-GCM (AAD = orgId, clé `PSP_ENCRYPTION_KEY`), **JAMAIS** renvoyés au client. `validerIdentifiants(provider, ids)` (`psp.service.ts`) : FAPSHI = `apiUser`+`apiKey`+`environnement` ; CAMPAY = `environnement` + (`token` **OU** `username`+`password`). `services/parametre-paiement.service.ts::lireConfigPaiement` renvoie une **vue SÛRE** : `provider`, `environnement`, `identifiantPublic` (= `username`/`apiUser`, NON secret), `misAJourLe`, `actif` — le mot de passe/clé/token reste chiffré et absent de la vue (régression : `JSON.stringify(vue)` ne contient jamais le secret). Écran ADMIN/PRESIDENT `frontend/src/components/ConfigPaiement.tsx` : **récap lecture seule** (identifiant **masqué** `Pj3cvh••••••liaQ` — c'est la moitié du couple d'auth, on en montre juste assez pour le reconnaître), **confirmation d'enregistrement PERSISTANTE** (`role="status"`, effacée à la modif suivante — pas seulement un toast fugace), **rappel de gouvernance** (compte au nom de l'asso, pas d'un dirigeant — **déclaratif** : l'API PSP n'expose PAS le titulaire du compte, vérifié — `/me/`, `/account/`, `/application/` → 404, `/balance/` sans nom — donc on conseille sans prétendre vérifier).
- **Démarrage** (`services/paiement.service.ts::demarrerPaiement`) : charge la config de l'org, déchiffre les creds, applique un **plafond SERVEUR au reste dû** (`MontantSuperieurAuResteError` → 400 ; ne JAMAIS croire le montant du client), avec un **montant minimum** = `env.PAIEMENT_MONTANT_MIN` (défaut 100) **servi au RUNTIME** via `GET /moi/paiement-disponible` → `{actif, montantMin}` (le front ne le déduit PLUS d'une variable de build `VITE_*` : **fin du couplage build-time front/back**, source unique serveur). La **collecte directe** (CAMPAY) exige le téléphone du membre (normalisé E.164 ; `TelephonePayeurRequisError` → 400 explicite si absent, jamais un 500 PSP). Le `Paiement` EN_ATTENTE est créé **APRÈS** l'appel PSP (pas de fantôme si le PSP échoue).
- **Confirmation** (`confirmerPaiement`) : le webhook n'est qu'un **DÉCLENCHEUR** — AUCUNE confiance à son corps ; on **RE-VÉRIFIE** le statut auprès du PSP (`verifierStatut`, appel authentifié) puis, sur REUSSI, on crée le `Versement` (invariant §5) de façon **IDEMPOTENTE** (`idempotenceKey = referenceExterne`, unique par org → rejeu/concurrence ne doublent jamais le versement) + un reçu best-effort. `prochaineAction(statutActuel, statutResolu)` = décision **PURE idempotente** (déjà tranché → RIEN). **Le versement utilise le montant STOCKÉ à l'initiation**, pas celui réaffiché par le PSP (le demo CamPay affiche « Montant 0 » sur les transactions de test — sans effet sur nous).
- **Mode de versement `MOBILE_MONEY`** — valeur ajoutée à l'enum `ModeVersement` (migration `mode_mobile_money`) et posée par `confirmerPaiement` (`paiement.service.ts`) : un versement issu d'une collecte PSP se distingue désormais d'un encaissement en espèces sur le reçu, le relevé et les exports. **Ajouter une valeur d'enum ne suffit PAS**, mais les listes de modes sont désormais **CONSOLIDÉES** : source unique `lib/modes-versement.ts` (`MODES_VERSEMENT` + `type ModeVersement`), importée par les 3 routes (versements/cagnottes/amendes) — plus de recopie à la main. La parité `MODES_VERSEMENT ↔ enum Postgres` est gardée EXÉCUTABLEMENT par `tests/modes-versement-parity.test.ts` (lit le schéma). Donc ajouter un mode = l'ajouter à l'enum (migration en deux temps, `ADD VALUE` puis usage, cf. Conventions) **et** à `MODES_VERSEMENT`, sinon le test casse. Côté front, DEUX sources uniques (le front ne peut pas importer le backend) : la valeur runtime `MODES_VERSEMENT` + type `ModeVersement` dérivé dans `lib/api/types.ts` (consommée TELLE QUELLE par toutes les listes déroulantes — création ET édition d'un versement, don de cagnotte, paiement d'amende), et les libellés `commun.modesVersement` (cf. i18n). Leur cohérence (union runtime ↔ libellés fr+en) est gardée par `frontend/src/lib/modes-versement.test.ts` — sans quoi un mode sans libellé afficherait une clé i18n brute via `cleI18n()`, en silence. **`MOBILE_MONEY` est saisissable À LA MAIN** (versement/don/amende), pas seulement posé par la confirmation PSP : un membre peut envoyer un MoMo hors flux intégré (directement sur le numéro du trésorier), qui doit pouvoir être enregistré comme tel. La provenance PSP n'est PAS portée par le `mode` mais par le lien `Paiement` (un versement issu du PSP a un `Paiement` rattaché ; un versement manuel n'en a pas) — le `mode` désigne le moyen de paiement, tout canal confondu.
  - **Backfill historique `AUTRE → MOBILE_MONEY`** (`prisma/backfill-mode-mobile-money.ts`, `npm run backfill:mode-momo`) : cible les `Versement` LIÉS à un `Paiement` et encore en `AUTRE` (un versement rattaché à un paiement est, par construction, du Mobile Money). **Dry-run PAR DÉFAUT**, `--apply` pour écrire, idempotent, `runUnscoped` (maintenance globale). Un `updateMany` échappant à l'audit applicatif, **la sortie console est la seule trace** → la capturer (`| tee`).
  - **⚠️ NE JAMAIS étendre ce backfill à `Recu.mode`.** Le reçu porte un SNAPSHOT du mode figé à la génération, et son PDF est mis en cache sur Blob : des membres ont déjà reçu un document affichant « Autre ». Réécrire `Recu.mode` ferait diverger la base du document remis — « compléter » le backfill serait une RÉGRESSION, pas une amélioration. Même logique que `Contribution.montantAttendu` : historisation par copie.
- **Webhooks PUBLICS** (`routes/paiements.route.ts`) : `POST /webhooks/fapshi` (`transId`) + `POST /webhooks/campay` (`reference`), factorisés par `confirmerParReference` : résout l'org **`runUnscoped`** (`await` OBLIGATOIRE dans le callback — PrismaPromise paresseuse, cf. §4.6) puis confirme DANS le contexte org, **toujours 200** (jamais de 4xx qui ferait boucler le PSP), best-effort + `observabilite.signaler` sur échec. **Modèle de confiance = déclencheur + re-vérification authentifiée**, strictement plus fort qu'un secret partagé. **Frontend — architecture applicative** (`frontend/src/`) :
- **Routing** (`App.tsx`) : `react-router-dom` déclaratif. Trois zones : pages publiques (`/`, `/login`, `/inscription`), console **plateforme** `/super-admin` (garde `SuperAdminRoute`, layout autonome **hors** `AppShell`), et pages tenant sous `<ProtectedLayout>` = `ProtectedRoute` (garde d'auth) + `AppShell` (coquille + nav) via `<Outlet/>`. **Routes statiques déclarées avant les paramétrées** (`/membres/nouveau` avant `/membres/:id`). **Largeur de contenu = `AppShell.classeLargeur(pathname)`** (liste de chemins codée en dur, appliquée AU contenu ET à la barre supérieure) : formulaires/réglages étroits (`max-w-3xl`), tables denses larges (`max-w-7xl` : `/audit`, `/membres`, `/utilisateurs`), défaut `max-w-6xl`. Elle DÉGRADE en douceur — une route non listée prend le défaut, jamais de casse — donc **ajouter une page dense = penser à l'inscrire dans `classeLargeur`** (sinon elle s'affichera en largeur intermédiaire au lieu de pleine).
- **Session** (`contexts/AuthContext.tsx` + `auth-context.ts`) : l'access token vit **uniquement en mémoire React** (jamais en `localStorage`). La persistance entre reloads repose sur le cookie httpOnly du refresh — au montage, `AuthContext` tente un `/auth/refresh` silencieux puis `/auth/me` pour réhydrater `user`. `useAuth()` expose `login`/`inscription`/`logout`/`changerLangue` + `user`/`accessToken`/`isAuthenticated`/`loading`. Il applique la langue (`appliquerLangue`, §4) **et la devise** (`appliquerDevise`, §5/F6) du serveur, enregistre le **pont d'auth** du client HTTP (`configurerAuthBridge` : token rafraîchi ↔ setState, session expirée ↔ logout) et arme le refresh proactif.
- **Client HTTP** (`lib/api.ts`) : `fetch` minimal, **`credentials: 'include'` obligatoire** (envoi du cookie refresh). Le token est passé explicitement en `Bearer` par appel. **Refresh-on-401** : au 1er 401 d'une requête authentifiée, `request()` appelle `/auth/refresh` (**dédupliqué** — une seule promesse en vol pour N requêtes concurrentes), remplace le token (`onTokenRefreshed` → `AuthContext`) et **rejoue la requête UNE fois** (`permettreRetry` anti-boucle) ; si le refresh échoue → `onSessionExpired` vide la session → `ProtectedRoute` redirige vers `/login`. `AuthContext` arme aussi un **refresh proactif** ~60 s avant l'expiration de l'access token (TTL 15 min). `ApiError` porte le statut HTTP ; `messageErreur(e)` distingue réponse d'erreur serveur vs rejet `fetch` (réseau/CORS). Base : `VITE_API_URL` (défaut `http://localhost:3000`) — en prod, proxy same-origin Vercel (`/api/*`). **Découpage par domaine (audit archi)** : `lib/api.ts` n'est plus qu'un **barrel** (`export * from './api/*'`) ; le cœur HTTP (`request`, `ApiError`, `messageErreur`, refresh-on-401, `configurerAuthBridge`) vit dans `lib/api/core.ts` (`request` EXPORTÉ pour les modules), les types transverses (`Paginated<T>`, `StatutContribution`, `ModeVersement`…) dans `lib/api/types.ts`, et **un module par domaine** `lib/api/<domaine>.ts` (membres, cagnottes, amendes, rapports…) exportant son objet `<domaine>Api` + ses types. **Tous les imports restent `from '@/lib/api'`** (le barrel préserve chaque nom exporté) — ne pas importer un sous-module directement. `tsc -b` garantit l'absence d'export dupliqué à travers le barrel.
- **Pages & data-fetching** : une page par écran dans `pages/` (liste/détail/formulaire par entité). Chargement de données **dans la page** (`useState`/`useEffect` + fonctions de `api.ts`) ; peu de hooks partagés (`hooks/useDashboard.ts`). Miroir des permissions dans `lib/roles.ts` pour masquer/afficher les actions selon le rôle (source de vérité = matrice backend).
- **Popovers/overlays ancrés à un déclencheur** : **rendus en portail** (`createPortal` dans `<body>`) + `position: fixed` calculée depuis le `getBoundingClientRect()` du déclencheur (recalcul au scroll capture + resize + changement de vue). **Raison structurelle** : `nk-reveal` anime en `forwards` → laisse un `transform` résiduel → chaque bloc animé devient un **contexte d'empilement** ; un popover simplement `absolute` (même `z-40`) reste piégé dans son bloc parent et se fait **recouvrir** par le bloc frère suivant (autre `nk-reveal`/transform/z-index) → illisible ET non cliquable (bugs vécus `/audit` puis `/fonctions`). Le portail l'immunise structurellement.
  - **`Button` rend `type="button"` par DÉFAUT** (`components/ui/Button.tsx`) : un `<button>` natif sans `type` vaut `submit`, donc tout bouton d'action posé dans un `<form>` soumettait le formulaire au lieu d'agir (bug vécu sur « Changer d'année »). **Soumettre exige donc `type="submit"` EXPLICITE** — ce que font déjà tous les boutons de soumission. Ne pas retirer ce défaut. **`ghost` n'est PAS un bouton d'action** : sans bordure ni soulignement au repos, il se lit comme une légende (même bug « Changer d'année », côté affordance cette fois) — réserver `ghost` aux zones où le contexte porte déjà l'affordance (barre d'icônes, ligne de tableau) et prendre **`outline` + icône** pour une action isolée au fil du texte.

Test volontairement ÉTROIT : les listes légitimement distinctes (`ROLES_APPROBATION`, `['ADMIN','PRESIDENT']`…) restent permises, les commentaires sont ignorés.
- `tests/modes-versement-parity.test.ts` — parité `MODES_VERSEMENT` (`lib/modes-versement.ts`) ↔ enum Postgres `ModeVersement` (lit le schéma). Liste autrefois recopiée à la main dans 3 routes (`MODE_ENUM`/`MODES`), désormais source unique ; anti-vacant `toBeGreaterThan(0)`.
- `tests/modes-versement-source-unique.test.ts` — **complément du précédent** : la parité garde la constante ↔ enum, PAS l'absence d'une NOUVELLE recopie ailleurs. Ce test balaie tout `src/**/*.ts` (hors `generated/` et `lib/modes-versement.ts`) et échoue si un fichier reconstruit l'ensemble des modes à la main — tableau littéral, union de type, OU **table de libellés** (objet dont les CLÉS couvrent la signature `{ ESPECES: …, MOBILE_MONEY: … }`) contenant à la fois `ESPECES` ET `MOBILE_MONEY` (un `'ESPECES'` isolé comme le défaut d'`amendes.route.ts` reste permis ; une clé i18n dottée `'commun.modeVersement.ESPECES'` du catalogue n'est PAS capturée). Motif calqué sur `roles-lists-parity.test.ts`. Deux défauts vécus l'ont motivé : (1) une 4ᵉ copie (union écrite à la main dans `releve.service.ts`) hors des 3 routes, invisible du test de parité ; (2) l'angle mort de la 1ʳᵉ version — deux **tables de libellés** `Record<string,string>` par mode dans `recu-pdf.service.ts` et `releve.service.ts` (documents remis aux membres où un mode absent rendait `undefined` en silence), que la détection tableau/union ne voyait pas. **Libellés des modes = SOURCE UNIQUE dans le catalogue i18n** (`commun.modeVersement.*`), lue par `lib/i18n.ts::libelleModeVersement(mode, langue)` (repli sur la valeur brute pour un mode hérité inconnu) — ne PAS refabriquer une table de traduction dans un service.
- **Deux modes de défaillance à connaître quand on écrit ce genre de test** : (1) le test **vacant** — s'il ne trouve plus rien à inspecter (prose reformulée, `readdirSync` vide), il passe au vert sans rien assertir ; d'où une garde `expect(n).toBeGreaterThan(0)` dans chacun. (2) le **sabotage inopérant** — vérifier qu'un test échoue en cassant le code ne prouve rien si la modification n'a pas pris (ancre de remplacement absente, chemin relatif erroné) : **contrôler que le sabotage s'est appliqué** avant d'interpréter un test resté vert. Les deux se sont produits pendant l'écriture de ces gardes.
- Quand la valeur est dérivable, la DÉRIVER plutôt que la garder : le libellé du fixture de purge est `` `couverture des ${SCOPED_MODELS.size} modèles` ``, plus aucun compteur à maintenir. Même recette pour le schéma ajv des préférences de notification — `properties: Object.fromEntries(TYPES_NOTIFICATION.map(...))` (`notifications.route.ts`) : ajouter un type de notification l'ouvre AUTOMATIQUEMENT à l'API. Les listes de modes de versement, autrefois recopiées à la main (`MODES`/`MODE_ENUM`), sont désormais consolidées dans `lib/modes-versement.ts` et gardées par `tests/modes-versement-parity.test.ts` (parité constante ↔ enum Postgres, cf. § Paiement).
- **⚠️ Piège ajv/Fastify : `additionalProperties: false` ne REJETTE pas, il SUPPRIME en silence.** Avec la config ajv par défaut de Fastify (`removeAdditional`), une clé inconnue du corps est retirée et la requête répond **200** — pas 400. Défaut vécu : `REUNION_RAPPEL` ajouté aux types de notification mais absent du schéma → `PATCH /notifications/preferences` acceptait la préférence, renvoyait 200, et la **jetait**. L'utilisateur bascule l'interrupteur, l'UI confirme, rien n'est enregistré. **Un test qui n'assère que le code HTTP ne voit RIEN** : asserter l'EFFET (ce qui a été écrit), pas le statut. C'est ce qui rend la dérivation ci-dessus structurelle et non cosmétique.

## Conventions
- **Français** partout : noms de fonctions métier, commentaires, messages d'erreur, commits.
- **Branches de feature** (`feat/...`), jamais de commit direct sur `main`. Merge `--no-ff`. Le PO exécute lui-même les commandes prod ; guider et vérifier.
- **Migrations réversibles** : une valeur d'enum Postgres ne peut pas être utilisée dans la transaction qui l'ajoute → séparer `ADD VALUE` et son usage (CHECK/backfill) en deux migrations.
- `backend/src/generated/` est **gitignoré** (régénéré au déploiement via `postinstall: prisma generate`).
- Nouveau flux sans requête HTTP (script, scheduler, seed) → l'envelopper dans `orgContext.run({ organisationId })` ou `runUnscoped()`, sinon fail-close.

## Déploiement
- **Backend → Railway** : `startCommand = npx prisma migrate deploy && npm run start` (migrations auto-appliquées au déploiement). `DATABASE_URL` = référence `${{ Postgres.DATABASE_URL }}`. `$PORT` injecté. **Le `&&` conditionne le boot** : si `migrate deploy` échoue (ex. `DATABASE_URL` invalide → `P1000`), `start` ne tourne pas, le healthcheck `/health` échoue, le déploiement passe **FAILED**, et Railway **continue de servir le DERNIER déploiement réussi**.
- **Watch Path `/backend/**` (Railway) — un push qui ne touche QUE `frontend/` ne déploie PAS le backend.** `watchPatterns: ["/backend/**"]` est versionné dans `backend/railway.json` **et** posé au dashboard (Root Directory du service = `/backend`, mais les watch patterns restent **relatifs à la racine du dépôt** — cf. `configFile: /backend/railway.json` stocké repo-root-relatif). Un merge front-only (ou doc-only) apparaît alors **`SKIPPED`** dans `railway deployment list` : c'est **normal**, pas un échec. Un changement sous `backend/` (dont `backend/prisma/` = migrations) déclenche bien un déploiement. Le Root Directory seul NE filtre PAS (sans watch pattern, tout push `main` déployait). Corollaire : **ne vérifier Railway que quand `backend/` a changé** ; pour un push front-only, vérifier Vercel.
- **Vérifier un déploiement = statut RÉEL, pas `/health`.** Un `/health` à 200 peut être servi par une ancienne image alors que le dernier déploiement a échoué. Utiliser le CLI `railway` (authentifié, projet `nkoni-backend`) : `railway deployment list` (le plus récent doit être **SUCCESS**, pas `BUILDING`/`FAILED`/`SKIPPED` — voir Watch Path) + `railway status` (le **deployment ID actif** doit être celui du push ; le précédent bascule `REMOVED`) ; logs d'échec via `railway logs --build <id>` (build) et `railway logs --deployment <id>` (start/migrate).
- **Frontend → Vercel** : racine projet = `frontend/`. `vercel.json` proxifie `/api/*` vers le backend Railway (**same-origin** → le cookie refresh fonctionne) + fallback SPA. Prod : `nkoni.vercel.app`.
- Variables backend : `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `JWT_ACCESS_TTL`, `JWT_REFRESH_TTL`, `CORS_ORIGIN` (liste séparée par virgules), `REFRESH_COOKIE_NAME`/`_PATH`, `BLOB_READ_WRITE_TOKEN`, `RECU_LINK_SECRET` (liens publics signés ; repli `JWT_ACCESS_SECRET`), `SENTRY_DSN` (observabilité, cf. 0.1 — absent = aucune alerte, l'app fonctionne mais les pannes sont invisibles), `NODE_ENV`.
  - **Canaux d'envoi** : `WHATSAPP_TOKEN`/`WHATSAPP_PHONE_ID` (canal primaire) et `RESEND_API_KEY`/`RESEND_FROM` (repli email, GA 0.4). Chacun est indépendamment optionnel — mais `lib/env.ts` **avertit en prod si les DEUX manquent** : reçus et relances ne partiraient alors nulle part.
  - **Paiement** : `PSP_ENCRYPTION_KEY` (32 octets ; sans elle la config PSP est indisponible et le bouton « Payer » n'apparaît jamais) et `PAIEMENT_MONTANT_MIN` (défaut 100).
  - Les warnings de `lib/env.ts` sont **NON bloquants et muets hors prod** — seuls les `JWT_*` sont en fail-fast au démarrage.
- Variable frontend (Vercel) : `VITE_SENTRY_DSN` — miroir de `SENTRY_DSN`. **DSN de projet Sentry DISTINCT** de celui du backend (un DSN front est public par nature, exposé dans le bundle : le partager donnerait un droit d'écriture sur le projet serveur).
